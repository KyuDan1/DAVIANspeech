# v73: 담당 성분을 정한 단순 인코더 조합

## 목적과 근거

새로운 큰 router를 학습하기 전에, 이미 선택·학습이 완료된 인코더들의 강점을
단순한 고정식으로 결합해 본다. 공식 제출 점수는 아직 확인하지 않은 연구 실험이다.

동일 개발셋에서 XLS-R mean head의 혼합 Voice EER은 0.12486, EAT adapted는
0.19243이었다. 반대로 혼합 Music EER은 XLS-R 0.25135, EAT adapted 0.13892였다.
XLS-R Voice EER은 codec 개발셋에서 clean/G.711/G.722 0.06667/0.08333/0.05000이나
Opus/G.711→Opus에서는 0.31667/0.33333이다. 독립 실행을 보장해 재학습한 SPEAR는
후자 두 채널에서 0.18333/0.23333이었다. 서로 다른 강점이 있다는 근거이지 실제
평가셋의 생성기나 채널 구성을 알아냈다는 뜻은 아니다.

## 결과를 보기 전에 고정한 두 방법

1. **XLS-R Voice + EAT Music**: 음성 fake는 XLS-R, 음악 fake는 EAT adapted.
2. **동일 가중치 Voice pair + EAT Music**: 음성 fake logit만 XLS-R/SPEAR를 50:50으로
   평균한다. 음악 fake는 같은 EAT adapted. 가중치·온도 탐색은 하지 않는다.

두 방법 모두 presence는 EAT adapted의 출력을 사용하며, 파일 fake는 다음으로 정한다.

`p_file = 1 - (1 - p_voice_fake * p_voice_present) * (1 - p_music_fake * p_music_present)`

조건부 성분 확률은 Voice/Music 출력 열에 그대로 유지한다. 존재 확률을 곱하는 것은
File 계산 안에서만 한다. 이 noisy-OR는 **독립성 근사**이며 성분 사건들이 정말 독립이거나
확률 보정이 완벽하다는 가정이 입증된 것은 아니다. 실제 지표로 효과를 확인해야 한다.
원래 EAT의 학습된 File head는 이 식에 들어가지 않는다.

학습 파라미터가 전혀 없는 모델이라는 뜻이 아니다. 기존 encoder/head는 학습된
모델이고, 이번 조합에서 **새로 학습하는 파라미터가 없다**는 뜻이다.

## 데이터와 독립성

4,577개 등록 development에서 동일 ID로 정렬한 기존 파일별 독립 추론 결과만 쓴다.
XLS-R/EAT는 완료된 전체 독립 추론을 재사용했다. SPEAR independent도 이번에
전체 4,577개를 파일별로 재추론하여 EER/ADS가 저장 평가와 같음을 확인했다.
다른 파일의 특징·예측·통계로 값을 바꾸는 계산은 없다. 조합 함수의 행 독립성,
존재하지 않는 성분 처리, logit 평균과 범위/NaN 검사를 포함한 7개 테스트가 통과했다.

처음부터 혼합 가중치나 hidden test 구성비를 역추정하여 맞추지 않는다.
개발 데이터는 혼합 3,700 / 음성 단독 316 / 음악 단독 561개로, 혼합이 80.8%다.
따라서 전체 ADS와 단독/혼합, 채널별 지표를 함께 제시한다.
다양한 모델의 최고 지표를 골라 합친 수치를 실제 공동 예측 성능으로 대신하지 않는다.

## 실행 상태

설정: `configs/component_composition_v73.yaml`.
실행: `scripts/evaluate_component_composition_v73.py`.
출력: `reports/component_composition_v73/`.

입력 체크섬과 코드를 고정한 뒤 위 두 조합의 계산을 완료했다. 아직 제출 후보의
최종 승격이나 실제 점수 상승 검증은 없다. 보고서의 “새로 학습한 파라미터” 필드 명칭을
정확히 하기 위해 첫 프로세스는 점수 계산 전에 중단하고 수정된 코드로 재시작했다.
가중치·식·입력 모델을 결과에 맞춰 바꾼 것은 아니다. 자동 제출하지 않는다.

## 완료한 개발 결과

| 방법 | File EER | Voice EER | Music EER | ADS |
|---|---:|---:|---:|---:|
| EAT adapted 단독 | 0.16885 | 0.19497 | 0.12908 | 0.83786 |
| XLS-R Voice + EAT Music | 0.12955 | 0.12625 | 0.12908 | 0.87125 |
| 동일 가중치 Voice pair + EAT Music | 0.12516 | 0.11579 | 0.12908 | 0.87554 |

두 조합 모두 존재 확률은 같은 EAT 값을 사용하므로 CPS는 0.999014로 같다.
혼합 3,700개의 ADS는 EAT 0.82903→동일 가중치 조합 0.87011이었다.
음성 단독 File EER은 EAT 0.18030→조합 0.18667로 소폭 악화했고,
Voice EER은 0.19942→0.17100으로 개선됐다. 모든 세부 지표가 좋아진 것은 아니다.

동일 codec 개발 600개에서 현재 최고 제출 앵커와 비교하면:

| 방법 | File EER | Voice EER | Music EER | ADS |
|---|---:|---:|---:|---:|
| 현재 제출 앵커 | 0.23333 | 0.20667 | 0.25333 | 0.76600 |
| XLS-R Voice + EAT Music | 0.17333 | 0.18000 | 0.21333 | 0.81333 |
| 동일 가중치 Voice pair + EAT Music | 0.15889 | 0.14000 | 0.21333 | 0.82856 |

같은 순서의 앵커 대비 동일 가중치 조합 ADS는 clean 0.89167→0.91667,
G.711 0.82000→0.89167, G.722 0.87167→0.90833,
Opus 0.65333→0.75222, G.711→Opus 0.66667→0.70333이었다.
G.711의 Voice EER만 보면 0.10000→0.11667로 악화하지만 File/Music 이득으로
해당 채널 ADS는 개선된다. 600개는 120개 기본 혼합의 상관된 5개 채널 변형이다.

이 수치들은 반복 사용한 development의 결과이며 **대회 점수 예측치가 아니다**.
미사용 원천·새 생성기에서 일반화하거나 리더보드 1위를 달성했다는 근거로 확대하지 않는다.

## 실제 통합 추론 검증

`src/component_composition_inference_v73.py`에서 세 모델을 같은 GPU에 올려
동일 원본 waveform을 각각 처리한 뒤 고정식을 적용한다. 분리 모델은 쓰지 않는다.
`scripts/verify_component_composition_v73.py`의 80파일 검사에서 저장 조합과
실제 추론의 최대 확률 차이는 3.87e-14, 역순 실행은 bit-exact였다.

B200에서 80파일의 정순·역순 합계 160회는 모델 로딩 후 약 38.35초,
peak allocated GPU 메모리는 12,179MiB였다. L4에서의 실행 시간·메모리를
직접 검증한 결과는 아니다. 제출 패키지·설치·오프라인 전체 실행 검증은 남아 있다.
검증 보고서: `reports/component_composition_v73/integrated_verified/report.json`.

추가로 같은 B200에 독립 프로세스 네 개(각각 세 모델)를 함께 올리는 처리량 검사를
완료했다. 디코딩/로딩 제외 80파일 처리 중앙값은 1개 9.072초→4개 6.755초로,
처리량 1.34배이며 모든 결과가 직렬과 bit-exact였다. 측정 조건이 위 160회 검사와
다르므로 두 절대 시간을 직접 비교하지 않는다. 연구 추론의 병렬 실행 기준과
메모리/제출 환경 제한은 `docs/gpu-colocation-v73.md`에 기록했다.

## 보호된 Suno 클립의 추가 경고

고정 v73으로 Suno 평가 클립 13개를 검사했다. File/Music은 0.5에서 13/13 Fake였으나,
Voice Fake는 4/13, Voice Presence는 0/13이었다. 이는 같은 양성 라벨만 있는 자료의
고정 임계값 결과이며 EER/CPS가 아니다. 특히 presence를 곱하는 File 결합의
일반화를 별도 확인해야 한다. 자세한 근거와 한계는 `docs/suno-frozen-v73-audit.md`에
기록했다. 이 결과로 기존 고정 후보를 다시 튜닝하지 않는다.
