# 공식 리더보드만으로 본 v18 EER 범위와 SOTA 요구량

작성일: 2026-09-04

이 문서는 로컬 평가의 truth, prediction, EER를 사용하지 않는다. 사용한 관측값은
DACON에 실제 제출해 받은 `Total/ADS/CPS`와, 제출물 사이에서 어떤 출력 열만
달라졌는지를 기록한 저장소 문서뿐이다.

## 결론

- v18에서 **정확히 식별되는 것은 세 EER 각각이 아니라**
  `0.5 F + 0.2 V + 0.3 M = 0.2636587302` 하나다.
- 과거 `twin_v1` probe로 복원한 File/Voice/Music EER
  `0.274143 / 0.215556 / 0.371429`는 그 당시 파이프라인의 정확한 값이다.
  v18의 값은 아니다.
- 현재 CPS를 유지하면서 표시된 1위 Total `0.837980`을 넘으려면 ADS가 최소
  `0.82116579`보다 커야 한다. v18 대비 필요한 ADS 상승은 `0.08482452`, 즉 현재
  가중 EER의 약 `32.17%`를 줄여야 한다.
- 한 축만으로 이 격차를 메우려면 File EER `0.169649`, Voice EER `0.424123`,
  Music EER `0.282748`만큼을 각각 낮춰야 한다. 현재 각 EER의 절대값을 모르므로
  어느 단일 축이 이것을 감당할 수 있는지도 공식 결과만으로는 확정할 수 없다.
- 다음 한 번은 다중 열 성능후보보다, 원본 v18에서 최종
  `MUSIC_FAKE_PROB`만 상수로 바꾼 probe가 정보가치가 높다. 단, 실제 제출한 v18
  archive에서 직접 파생되어 나머지 네 열이 동일하다는 보장이 전제다.

표기에서 `F`, `V`, `M`은 각각 v18의 File, Voice, Music EER다.

## 1. 현재 공식 점수가 고정하는 평면

대회식은 다음과 같다.

```text
ADS = 1 - (0.5 F + 0.2 V + 0.3 M)
```

v18의 공식 ADS `0.7363412698`을 넣으면 다음 식 하나만 얻는다.

```text
0.5 F + 0.2 V + 0.3 M = 1 - 0.7363412698
                          = 0.2636587302
```

미지수는 세 개인데 독립식은 하나이므로 자유도가 두 개 남는다. 따라서 v18 ADS가
상승했다는 사실만으로 `Music이 얼마나 좋아졌다`, `File이 현재 얼마다`와 같은
주장은 할 수 없다. 한 축의 개선과 다른 축의 악화가 상쇄됐을 수도 있다.

### 수학적으로 가능한 범위

대회가 공개한 이산 EER 구현에서 역방향 점수는 EER가 `0.5`를 넘을 수도 있으므로,
정의만으로 안전한 범위는 각 EER `0 <= E <= 1`이다. 이 범위와 위 식만 사용하면:

| 축 | 엄밀한 가능 범위 |
|---|---:|
| File EER | `0 <= F <= 0.5273174604` |
| Voice EER | `0 <= V <= 1` |
| Music EER | `0 <= M <= 0.8788624340` |

학습된 확률의 방향이 뒤집히지 않았다는 실무 가정, 즉 각 EER가 `[0, 0.5]`에
있다고 가정하면 범위는 다음과 같이 줄어든다. 이것은 합리적인 운영 가정이지만
공식 ADS만으로 증명된 사실은 아니다.

| 축 | `0 <= E <= 0.5` 가정하의 범위 |
|---|---:|
| File EER | `0.0273174604 <= F <= 0.5` |
| Voice EER | `0 <= V <= 0.5` |
| Music EER | `0 <= M <= 0.5` |

공식 메모상 v32는 v18에서 File 열만, v33은 v32에서 Music 열만 바꿨다. 실제 ADS로
알 수 있는 것은 절대값이 아니라 다음 **변화량**이다.

```text
F_v32 - F_v18 = (0.7363412698 - 0.7234126984) / 0.5
              = 0.0258571428

M_v33 - M_v18 = (0.7234126984 - 0.7148412698) / 0.3
              = 0.0285714287
```

즉 두 변경 모두 해당 축을 악화시켰다. 이 차분은 제출 메모대로 다른 열이 실제로
동일할 때 정확하다. 여기에 v32와 v33의 해당 EER도 `0.5` 이하라는 운영 가정을
추가하면 v18의 범위는 다음까지 좁힐 수 있다.

| 축 | 공식 차분 + 비역전 가정하의 범위 |
|---|---:|
| File EER | `0.0444603176 <= F <= 0.4741428572` |
| Voice EER | `0 <= V <= 0.5` |
| Music EER | `0 <= M <= 0.4714285713` |

여전히 실제 병목을 하나로 지목하기에는 매우 넓다. v19와 inv4-w30은 세 authenticity
열을 함께 바꿨기 때문에 ADS 하락만으로 축별 변화량도 분리할 수 없다.

## 2. 왜 예전 probe를 v18 분해에 사용할 수 없는가

과거 쌍둥이 제출 세 개는 서로 모델과 나머지 출력이 동일했기 때문에 당시
파이프라인의 EER를 정확히 복원했다.

| 제출 | ADS | 복원 결과 |
|---|---:|---:|
| `twin_v1` | `0.7083888889` | anchor |
| `probe_voice_v1` | `0.6515000000` | Voice EER `0.2155555555` |
| `probe_music_v1` | `0.6698174603` | Music EER `0.3714285713` |
| 위 세 값에서 유도 | - | File EER `0.2741428572` |

상수 열의 EER는 대회 ROC 구현에서 정확히 `0.5`이므로 이 복원은 **twin 자체에는
정확하다**. 문제는 twin과 v18이 같은 파이프라인이 아니라는 점이다.

- twin은 HTDemucs stem, XLS-R-2B, XLS-R/ArtifactNet music 결합, presence gate와
  component max를 사용했다.
- v18은 그 뒤 계보에서 원본 오디오 EAT/SPEAR temporal branch, MERT,
  fakeprint, channel/component-invariant head를 추가했고 File/Voice/Music 출력이
  모두 바뀔 수 있다.
- EER는 확률의 절대 보정값이 아니라 전체 표본의 순위와 ROC 교차점으로 계산된다.
  작은 logit residual도 교차점 주변 순서를 바꾸므로, 과거 EER에 ADS 개선분을
  비례 배분하거나 단순 스케일링할 근거가 없다.

같은 이유로 LME anchor/probe가 준 Voice EER `0.22`, `musicorig` anchor/probe가 준
Music EER `0.431429`도 각각 그 파이프라인의 값일 뿐 v18의 절대값이 아니다.

참고로 다음은 **증명되지 않은 가정**이 어느 정도 강한지를 보여 주는 계산이다.
만약 v18의 세 축이 twin보다 하나도 악화되지 않았다고 가정하면 위 식으로부터:

```text
0.218238 <= F <= 0.274143
0.075794 <= V <= 0.215556
0.278254 <= M <= 0.371429
```

까지 좁혀진다. 그러나 공식 제출은 세 축의 동시 비악화를 검증하지 않았으므로 이
구간을 v18의 측정값처럼 사용하면 안 된다. 이는 계획용 가설의 민감도 예시일 뿐이다.

## 3. 1위까지 필요한 개선량

현재 표시된 1위는 Total `0.837980`, ADS `0.821160`, CPS `0.98932`다. 표시 자릿수의
반올림 때문에 `0.9 * ADS + 0.1 * CPS`는 Total과 약 `0.000004` 차이가 난다.

v18 CPS `0.9893078836`을 그대로 유지한다고 할 때 표시된 1위 Total을 넘기 위한
ADS 경계는 다음과 같다.

```text
ADS_required = (0.837980 - 0.1 * 0.9893078836) / 0.9
             = 0.8211657907

ADS gap      = 0.8211657907 - 0.7363412698
             = 0.0848245209
```

1위의 표시 ADS `0.821160`만 넘기는 격차는 `0.0848187302`다. 실제 내부 점수의
반올림 경계를 모르므로 운영 목표는 `0.82117`보다 약간 높은 값으로 잡아야 한다.

목표 가중 EER는 `0.1788342093` 미만이다. 현재 `0.2636587302`에서 절대
`0.0848245209`, 상대 `32.1721%` 이상 줄여야 한다.

### 한 축 또는 여러 축으로 달성하는 조건

`dF`, `dV`, `dM`을 각 EER의 감소량이라고 하면 반드시 다음을 만족해야 한다.

```text
0.5 dF + 0.2 dV + 0.3 dM > 0.0848245209
```

| 개선 배분 | 필요한 EER 감소량 |
|---|---:|
| File만 개선 | `dF > 0.1696490418` |
| Voice만 개선 | `dV > 0.4241226046` |
| Music만 개선 | `dM > 0.2827484030` |
| 세 축을 같은 절대량 개선 | 각각 `> 0.0848245209` |
| File과 Music을 같은 절대량 개선, Voice 동결 | 각각 `> 0.1060306511` |
| 세 축을 같은 비율로 개선 | 각각 현재 EER의 `> 32.1721%` |

따라서 Voice 단독 달성은 현재 Voice EER가 최소 `0.424123`이어야만 수학적으로
가능하다. 과거 두 Voice probe는 약 `0.216~0.22`였으므로 가능성이 낮아 보이지만,
그 값은 v18 측정이 아니므로 이는 추정이다. Music 단독 달성 가능 여부는 현재 Music
EER가 `0.282748`보다 큰지에 달려 있고, 이것이 Music probe를 먼저 할 실질적인
이유다. File도 현재 EER가 `0.169649`보다 커야 단독 달성이 가능하다.

## 4. 다음 공식 제출의 정보가치

### 선택지 A: 다중 열 성능후보

File/Voice/Music을 동시에 바꾼 후보는 점수가 오르면 리더보드 갱신에는 도움이 되지만,
ADS 하나로는 어느 축이 기여했는지 알 수 없다. 점수가 내리거나 동률이면 상쇄인지,
세 축 모두 무효인지도 분리할 수 없다. v19와 inv4-w30이 바로 이 경우다.

한 축만 바꾼 성능후보는 ADS 차이로 그 축의 **EER 변화량**을 정확히 알 수 있어
다중 열 후보보다 낫다. 다만 baseline EER 절대값은 여전히 모른다.

### 선택지 B: v18 한 열 상수 probe

실제 제출된 v18과 나머지 모든 열이 같고 `MUSIC_FAKE_PROB`만 최종 CSV에서 상수
`0.5`라면 한 번의 제출로 다음을 정확히 얻는다.

```text
M_v18 = 0.5 - (ADS_v18 - ADS_music_probe) / 0.3
```

이 제출은 순위를 올리지는 않지만 다음을 즉시 결정한다.

1. Music 단독으로 SOTA 격차를 메울 수 있는 오차량이 실제로 남아 있는가.
2. 현재 가중 손실 중 Music의 정확한 몫은 얼마인가.
3. 이후 Music-only 성능후보의 공식 변화량을 절대 EER로 환산할 수 있는가.

한 probe 뒤에도 `0.5F + 0.2V` 한 식에 두 미지수가 남는다. 완전 분해에는
`VOICE_FAKE_PROB` 상수 probe를 한 번 더 제출하면 되고, File은 남은 식으로
유도할 수 있다. 즉 이미 존재하는 정확한 v18 anchor를 재사용할 수 있다면 완전
분해 비용은 두 제출이다.

### 추천

현재 다음 한 번은 **v18 Music constant probe**를 추천한다. 이유는 다음과 같다.

- v18과 1위의 ADS 격차 `0.084825`는 작은 residual 후보 한 번으로 닫힐 규모가
  아니며, 현재 공식 이력에는 새 다중 열 후보가 이 폭을 낼 근거가 없다.
- 최근 v19, v32, v33, inv4-w30은 모두 v18보다 낮았다. 또 다중 열 제출은 실패
  원인을 식별하지 못해 같은 종류의 제출을 반복하게 했다.
- Music probe 한 회는 가장 큰 것으로 추정되는 축의 절대 EER와 `0.282748` 임계값을
  직접 검증한다. 이후에는 Music-only 또는 File-only 후보를 내어 성능과 인과
  진단을 동시에 얻을 수 있다.

단, 아래 전제 중 하나라도 충족하지 못하면 probe를 제출해서는 안 된다.

1. 공식 v18에 제출한 원본 archive와 동일한 모델/코드를 사용한다. 문서에 기록된
   archive SHA-256은
   `b3f7082a268acf08bbc1bfc36a25ced1be6232d81c7cf79be7ab9f890ae2d845`다.
2. probe override는 모든 추론과 File 계산이 끝난 뒤 최종
   `MUSIC_FAKE_PROB` 열에만 적용한다.
3. 같은 입력에 대해 probe와 anchor의 나머지 네 출력 열이 bit-exact이고 행 순서도
   동일함을 확인한다.

원본 v18 archive를 재사용할 수 없고 재빌드 동일성을 보장할 수 없다면 기존 v18 ADS를
anchor로 쓰면 안 된다. 그 경우에는 재빌드 anchor를 먼저 공식 제출해야 하므로 Music
하나를 측정하는 비용이 두 회, 완전 분해 비용이 세 회가 된다. 제출 횟수가 부족하면
그때는 pure diagnostic 대신 **exact-v18에서 한 authenticity 열만 바꾼 성능후보**를
우선하되, 여러 열을 동시에 바꾼 후보는 피한다.

## 5. exact-v18 Music probe 빌드 검증

위 전제를 만족하는 probe를 `scripts/build_v18_music_probe.py`로 만들었다. builder는
다음 공식 v18 identity와 inventory가 하나라도 다르면 생성을 거부한다.

| 항목 | exact official v18 |
|---|---:|
| archive | `channel_invariant_moe_v18.zip` |
| SHA-256 | `b3f7082a268acf08bbc1bfc36a25ced1be6232d81c7cf79be7ab9f890ae2d845` |
| archive bytes | `7,907,816,613` |
| expanded bytes | `7,907,795,069` |
| members | `107` |
| `script.py` SHA-256 | `954f30bcaa621aca1055db0c0ccba119dc5ae9b38cf55874f59807e355826de6` |
| `requirements.txt` SHA-256 | `978befe6e5c8a064cddd2690e7e55b4b153f87eabf0dcf3b0604a567f4edd6ed` |

builder는 ZIP을 임시 파일로 스트리밍 복사하고 `script.py`만 바꾼다. 새 entrypoint는
마지막 invariant fusion까지 모두 끝난 다음 CSV의 `MUSIC_FAKE_PROB`만 행별 상수
문자열 `0.5`로 바꾸고 원자적으로 교체한다. 다른 표본의 값이나 통계를 읽어 보정하지
않는다. 나머지 106개 member의 uncompressed size와 CRC가 base와 같은지 확인한 뒤에만
최종 파일명으로 이동한다.

최종 archive 검증값은 다음과 같다.

| 항목 | Music probe |
|---|---:|
| archive | `v18_music_probe_v1.zip` |
| SHA-256 | `2bd5fa1652831596280e7669e4529edc1d026c04856dbaac77514322894c31d1` |
| archive bytes | `7,907,813,105` |
| expanded bytes | `7,907,796,725` |
| members | `107` |
| patched `script.py` SHA-256 | `37640507e4df5fd63e00691da4447ea6a74ffbac418f0be35c5a24d9f0033c91` |
| top level | `model/`, `script.py`, `requirements.txt` |
| duplicate / unsafe / symlink | `0 / 0 / 0` |
| full ZIP CRC | 통과 |

파일명은 30자 이하이며, 압축 10 GB와 해제 32 GB의 더 엄격한 decimal-byte 경계를
모두 만족한다. `requirements.txt`는 official v18과 byte-exact라 서버 기본 패키지를
새로 중복 지정하지 않는다.

사용자가 제공한 Suno MP3 세 개로 네트워크 비활성 환경변수를 설정하고 exact anchor와
probe entrypoint를 각각 전체 실행했다. anchor `267.103초`, probe `147.533초`에
성공했으며 다음 CSV 필드는 세 행 모두 문자열 단위로 동일했다.

```text
ID
FILE_FAKE_PROB
VOICE_FAKE_PROB
VOICE_PRESENT_PROB
MUSIC_PRESENT_PROB
```

probe의 `MUSIC_FAKE_PROB`만 세 행 모두 정확히 `0.5`였다. 이 smoke는 label, EER,
blind v8 또는 retrospective truth를 읽지 않은 실행 건전성 검사다. API 제출과 Git
commit은 수행하지 않았다.
