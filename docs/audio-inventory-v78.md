# v78: 학습 준비 단계의 공유 스토리지 병목

GPU 메모리가 남아도 데이터 준비가 오래 걸리는 원인을 좁혔다. 기존
`src.pipeline.find_audio_files`는 `Path.iterdir()`로 만든 각 경로에 `is_file()`을
호출한다. 공유 파일시스템에서는 파일마다 별도 메타데이터 요청이 발생한다.

TRAIN `channel_invariant_factorial_train_v1/audio`에서 측정한 결과:

- `os.scandir`의 DirEntry file-type 정보로 3,000개를 찾는 데 0.01255초.
- 같은 파일 목록의 첫 100개에만 `Path.is_file()`을 호출하는 데 2.17454초.

이는 **파일 목록 조회 측정**이며, 전체 학습이 몇 배 빨라진다는 측정은 아니다.
동일 수의 파일 비교가 아니므로 두 시간을 나눠 전체 속도 향상률을 만들지 않는다.
모듈 import, waveform 읽기, ID 분할 검사 등의 다른 대기도 존재할 수 있다.

새 `src/audio_inventory_v78.py`는 파일 순서, 확장자, symlink 추적, 중복 stem 거부,
없는/빈 폴더 처리 의미를 유지하면서 DirEntry를 사용한다. 테스트 3개가 통과했다.
새 함수를 실제 TRAIN 폴더에 적용한 별도 실행은 0.01885초였으며, 반환한 파일 ID
3,000개가 등록된 truth ID 전체와 동일함을 확인했다. 라벨이나 오디오를 변경하지 않았다.

진행 중인 v74/v76 실행의 함수나 frozen source를 바꾸지 않았다. 이 함수는 아직 해당
실행에 연결하지 않았으며, 이후 새 실행의 데이터 로더에 명시적으로 연결하고 입력 ID와
manifest 해시 동등성을 확인해야 한다. 현재 실행을 속도가 느리다는 이유로 중복 시작하지 않는다.

## 실제 데이터 준비 연결 완료

`scripts/cache_training_inventory_v78.py`에서 새 프로세스에만 빠른 조회를 연결했다.
TRAIN 18,738개와 개발 4,577개의 **ID와 순서**, 원천 manifest SHA가 완료된 EAT parent
실험과 같음을 확인했다. 보호 역할 전체와의 원천 분리도 재검사했다.
출력은 `reports/training_inventory_v78/`이며 오디오를 디코딩하거나 학습하지 않았다.

전체 loader/분리 확인은 70.14초, 파일 목록 조회 합계는 67.68초, 전체 캐시 생성은
73.22초였다. 폴더별로 symlink·메타데이터 상태가 달라 앞의 3,000개 단일 폴더
측정처럼 모두 수십 ms로 끝나지는 않는다. 이 캐시는 WavLM v79의 실제 학습 준비에서
원천·테이블 해시를 다시 확인한 뒤 사용했다.

첫 실행은 NumPy 1.26에서 기존 진단 코드의 Unicode ndarray `+` 연산이 실패해
종료됐다. 실패한 실행을 성공으로 취급하지 않는다. 원래 파일은 바꾸지 않고 별도
`src/diagnostic_axes_compat_v78.py`로 동일 RR/RF/FR/FF 문자열을 구성했다.
레이블 보존·문자열 결과 테스트를 통과한 후 캐시 생성을 완료했다.
