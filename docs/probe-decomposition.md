# 프로브 제출로 얻은 File / Voice / Music EER 분해

## 1. 왜 했나

리더보드는 가중합 하나만 돌려준다.

```text
ADS = 0.5 × (1 - FILE_EER) + 0.2 × (1 - VOICE_EER) + 0.3 × (1 - MUSIC_EER)
```

미지수가 셋인데 식이 하나다. 그래서 제출 한 번이 주는 정보는 "좋아졌다 / 나빠졌다"
1비트뿐이고, v6에서 ADS가 `0.0576` 떨어졌을 때도 Music이 나빠진 건지 Voice가
나빠진 건지 알 수 없었다. 로컬 평가는 대안이 되지 못했다 — v10 로컬 예측이
ADS `0.862`였는데 실제는 `0.6763`으로, 노이즈가 아니라 반대 방향이었다.

그래서 제출 세 번을 성능 개선이 아니라 **측정**에 썼다.

## 2. 방법

한 확률 컬럼을 상수로 덮어쓰면 그 컬럼의 EER이 정확히 `0.5`로 고정된다. 대회
평가 페이지가 공개한 공식이 `EER = (fpr[idx] + fnr[idx]) / 2` (단, `idx`는
`argmin |fpr - fnr|`)인데, 점수가 모두 같으면 ROC가 `fpr = [0, 1]`,
`tpr = [0, 1]` 두 점으로 축약되고 두 점 모두 `|fpr - fnr| = 1`로 동률이라, 어느
쪽을 고르든 `(0+1)/2 = (1+0)/2 = 0.5`가 된다. 상수값이 0이든 0.5든 1이든,
표본 수가 2든 1,200이든, 양성 비율이 얼마든 결과는 정확히 `0.5`다.

나머지 두 컬럼은 건드리지 않으므로 다른 두 항은 그대로다. 따라서 프로브를 씌우지
않은 실행과의 차이가 그 항을 지목한다.

```text
MUSIC_EER = 0.5 - (ADS_anchor - ADS_probe) / 0.3
VOICE_EER = 0.5 - (ADS_anchor - ADS_probe) / 0.2
FILE_EER  = ((1 - ADS_anchor) - 0.2 × VOICE_EER - 0.3 × MUSIC_EER) / 0.5
```

### 앵커를 따로 제출한 이유

`ADS_anchor`로 과거 기록인 `0.7075317460`을 그대로 쓰려 했으나, 그 점수를 낸
zip이 이 머신에 없어 재빌드가 동일하다고 보장할 수 없었다. 앵커 오차는 복원값에
음악은 3.3배, 음성은 5배로 증폭된다.

| 앵커 오차 | MUSIC_EER 편향 | VOICE_EER 편향 |
| ---: | ---: | ---: |
| ±0.01 | ±0.033 | ±0.050 |
| −0.017 | −0.058 | −0.087 |

구분하려던 폭(예: Voice 0.1 대 0.2)보다 편향이 커서 측정이 무의미해질 수 있었다.
그래서 프로브를 씌우지 않은 **쌍둥이 패키지**를 먼저 제출해 그 ADS를 앵커로 썼다.
쌍둥이는 프로브와 모델 체크섬, `src/`, `requirements.txt`가 모두 동일하고
`script.py`의 프로브 블록 유무만 다르다. 제출 3회, 미지수 3개로 정보량이 최소다.

## 3. 제출 내역과 결과

2026-08-30 KST 00:00~00:08, 일일 quota 3회를 모두 사용했다.

| # | 패키지 | 변경 | Total | ADS | CPS |
| --- | --- | --- | ---: | ---: | ---: |
| ① | `twin_v1.zip` | 없음 (앵커) | 0.7364824974 | **0.7083888889** | 0.9893249735 |
| ② | `probe_music_v1.zip` | `MUSIC_FAKE_PROB = 0.5` | 0.7017682116 | 0.6698174603 | 0.9893249735 |
| ③ | `probe_voice_v1.zip` | `VOICE_FAKE_PROB = 0.5` | 0.6852824974 | 0.6515000000 | 0.9893249735 |

세 행 모두 `0.9 × ADS + 0.1 × CPS = Total`이 소수점 10자리까지 일치한다. CPS가
세 행에서 동일한 것도 예상대로다 — 프로브는 presence 컬럼을 건드리지 않는다.

파이프라인 구성은 `fdf64bd` 계열이다. PANNs presence, HTDemucs 분리, XLS-R-2B
음성 판별, 음악은 `0.5 × XLS-R + 0.5 × ArtifactNet`, presence gate `0.7`,
파일 결합은 활성 성분의 max.

### 앵커 검증

재빌드 앵커 `0.7083888889`는 팀 기준 제출 `0.7075317460`과 `+0.00086` 차이다.
CPS도 `+0.00015` 차이에 그친다. 재빌드가 기준 제출과 사실상 동등하다는 뜻이고,
동시에 앵커를 따로 낸 것이 과했다기보다 **차이가 실제로 존재했음**을 보여준다.
그 `+0.00086`을 무시했다면 Music은 `0.0029`, Voice는 `0.0043` 틀어졌을 것이다.

## 4. 분해 결과

```text
MUSIC_EER = 0.5 - 0.0385714286 / 0.3 = 0.3714
VOICE_EER = 0.5 - 0.0568888889 / 0.2 = 0.2156
FILE_EER  = (0.2916111111 - 0.2×0.2156 - 0.3×0.3714) / 0.5 = 0.2741
```

세 값 모두 `[0, 0.5]` 안이다. 범위를 벗어났다면 앵커가 틀렸거나 채점 서버의 EER
관례가 다르다는 신호였을 텐데, 그렇지 않았다.

### 손실 기여도

가중 EER `0.2916111111`을 셋으로 나누면 이렇다.

| 항목 | EER | 가중치 | 가중 기여 | 손실 비중 |
| --- | ---: | ---: | ---: | ---: |
| **File** | 0.2741 | 0.5 | 0.1371 | **47%** |
| **Music** | 0.3714 | 0.3 | 0.1114 | **38%** |
| **Voice** | 0.2156 | 0.2 | 0.0431 | **15%** |

### 각 항을 완벽하게 만들었을 때 도달점

| 가정 | ADS | Score |
| --- | ---: | ---: |
| File EER → 0 | 0.8455 | 0.8598 |
| Music EER → 0 | 0.8198 | 0.8368 |
| Voice EER → 0 | 0.7515 | 0.7753 |
| (현재) | 0.7084 | 0.7365 |

Score 0.8에 필요한 ADS는 `0.778964`, 현재와의 격차는 `+0.070575`다. Voice 하나만
완벽하게 만들어도 목표에 못 미친다. 다만 File은 Voice와 Music에서 파생되므로 위
표의 세 줄은 서로 독립이 아니다.

## 5. 이 숫자가 바꾸는 것

`VOICE_EER = 0.2156`이 가장 중요한 발견이다. 로컬에서 측정한 값들과 비교하면
이 값이 어디서 나올 수 있는지가 좁혀진다.

| 조건 | Voice EER |
| --- | ---: |
| 한국어 순수 음성 + MeloTTS (VITS 계열) | 0.0000 |
| 한국어 순수 음성 + Audio8 (DualAR codec-LLM) | 0.0200 |
| 위에 64kbps MP3 / 8kHz 전화대역 / 15dB 잡음 | 0.0000 |
| 진짜 음악을 섞고 HTDemucs로 분리 (SNR +5 ~ −5dB) | 0.33 ~ 0.48 |
| **실제 대회 (이번 측정)** | **0.2156** |

`0.2156`은 순수 음성 조건에서는 나올 수 없는 값이고 혼합 조건 범위 안쪽이다.
즉 대회 테스트셋에 음성·음악 혼합 파일이 상당수 있고, 거기서 **진짜 음성이 가짜로
찍히고 있다**.

이 오경보의 규모는 따로 측정해 두었다. 진짜 한국어 음성에 진짜 GTZAN 음악을 섞고
HTDemucs로 분리한 뒤 vocal stem을 판별했을 때, 가짜가 하나도 없는데도:

| 조건 | 진짜인데 P(fake) > 0.5 |
| --- | ---: |
| 순수 음성 (분리 안 함) | 4% |
| 음성만 분리 통과 (음악 없음) | 4% |
| 음악 SNR +5dB → 분리 | 32% |
| 음악 SNR 0dB → 분리 | 52% |
| 음악 SNR −5dB → 분리 | 76% |

HTDemucs 자체는 무죄다. 음악 없이 통과시키면 오경보가 4%로 그대로다. 문제는
**음악이 섞였을 때 vocal stem에 남는 잔재**이고, 탐지기가 그것을 생성 흔적으로
읽는다.

지금까지의 MoE 작업은 모두 음악 전문가 추가였다. 그러나 음악은 손실의 38%이고,
그보다 큰 47%가 File이며, File은 혼합 파일에서 voice 오경보가 나면 함께 오염된다.

## 6. 한계

- 세 값은 `fdf64bd` 계열 패키지에 대한 것이다. 다른 구성의 분해는 그 구성으로
  다시 측정해야 한다.
- 혼합 오경보 실험은 GTZAN 음악을 인위적으로 섞은 것이라 대회 오디오의 실제 혼합
  양상과 다를 수 있다. 표본도 SNR당 25~40쌍으로 작다.
- 대회 테스트셋에서 혼합 파일의 비율은 여전히 모른다. Voice EER `0.2156`이
  "혼합이 적은데 많이 틀림"인지 "혼합이 많은데 적당히 틀림"인지 구분되지 않는다.

## 7. 다음 후보

우선순위는 혼합 오디오에서 voice 오경보를 줄이는 것으로 확정됐다.

1. 분리 후처리 — vocal stem의 음악 잔재 게이팅/마스킹
2. 원본과 stem 점수 결합 — v10에서 시도했으나 근거 없이 가중치를 정했다
3. `MUSIC_PRESENT`가 높을 때 `VOICE_FAKE`를 보수적으로 보정
4. `--pooling logmeanexp` — 미제출. 학습 파라미터가 없어 도메인 과적합 위험이
   없고 세 항 모두에 걸린다

그리고 이제 로컬 검증 기준이 생겼다. 혼합 평가셋에서 Voice EER이 `0.2156` 근처로
재현되는 조건을 찾으면 그것이 대회 분포의 대리 지표가 된다. 지금까지 로컬 평가가
빗나간 이유가 혼합을 제대로 다루지 않아서였을 가능성이 크다.

## 8. 재현 방법

```bash
# 앵커와 프로브 빌드 (모델 파일은 동일, script.py 만 다름)
python scripts/build_submission.py --output-dir twin        ...        # 앵커
python scripts/build_submission.py --output-dir probe_music ... \
    --probe-column MUSIC_FAKE_PROB
python scripts/build_submission.py --output-dir probe_voice ... \
    --probe-column VOICE_FAKE_PROB

# quota 가 열리면 순서대로 업로드 (하나 실패하면 나머지를 쏘지 않는다)
python scripts/submit_dacon.py --config .config --wait \
    --probe twin_v1.zip:"앵커" \
    --probe probe_music_v1.zip:"진단용 - MUSIC_FAKE_PROB 상수" \
    --probe probe_voice_v1.zip:"진단용 - VOICE_FAKE_PROB 상수"

# 리더보드의 ADS 세 개를 넣어 분해
python scripts/decode_probes.py --anchor 0.7083888889 \
    --music-probe 0.6698174603 --voice-probe 0.6515
```

프로브 제출은 의도적으로 점수가 낮게 나온다. 동의사항의 "사람이 예측한 정보" 조항과
오해되지 않도록 제출 메모에 진단 목적임을 명시했다.
